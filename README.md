# doc-version-executor v5

## 本轮修改

- 纯章节更名按唯一相同正文匹配，不误报删除和新增。更名同时改正文而无法确定对应关系时，明确报告“章节对应待核对”，不猜测。
- 覆盖版本表前、版本表后到首个二级标题的引言；同名章节不再覆盖；代码围栏内的标题不分章；重排单独报告。
- 仅排除顶部明确标注的例行更新时间值；保留同行实质文字、其他日期和完整引言。存在该字段时实际更新，不新建“顶部时间”列。操作说明仍来自已确认输入，不由算法擅自改写。
- 副本完整含版本表、旧行检查、有限重试等是既有能力，本轮继续回归，不冒充新增功能。

## 三个工作流

1. VT 版本协议测试：输入 VT01～VT23 或 all。先跑15项差异回归，再在真实 Notion 的新建测试文档上运行所选测试；原样本只读，结果写入新 v5 总表，编号连续；旧表不改。日志作为运行附件保留。
2. 改坏执行器检查：14份缺陷变体分别运行全部23项离线测试和15项差异检查；预测与实际必须完全一致。完全离线，不使用 Notion 令牌，不修改页面；离线样本只证明模拟环境行为，不代替真实 Notion 验收。
3. 正式运行：版本管理：输入 doc、archive、note、who；who没有默认AI。验收先使用新建测试文档，不直接操作真实协议。结果只有“版本成立”或“版本管理失败”。

所有工作流只在明确发起运行时执行；提交代码不会自动启动。VT与正式版本管理互斥运行，不自动取消已开始的运行。测试运行固定到该次事件的提交，不在执行中跟随分支最新内容。

## Notion 内的审核和核验

提交前展示仓库、分支、文件清单和可查看的实际差异；批准后内容变化需重新核对。提交后从 GitHub 读回文件，通过 Git blob SHA及完整文件 SHA-256 对照交付包。每个工作流启动前再执行 verify-release.mjs，与 release-manifest.json 逐字节比较；不一致立即停止。

运行前展示工作流、代码版本、输入和写入范围，使用 MCP 发起同一请求；之后读取真实运行、日志、结果和 Notion 记录。原生 Notion 审核框未必展示完整差异，不能替代差异文件。清单是可审计的一致性证据，不是数字签名，也不能阻止同时篡改文件与清单的仓库管理员；提交编号应单独核对。

## 本地检查

```sh
node verify-release.mjs
node vt/diff-tests.mjs
node vt/run-vt.mjs --case VT01 --fake --offline
node vt/mutate.mjs
```

--fake 单独使用仍会读取真实样本；只有 --fake --offline 不访问真实 Notion。固定离线样本在 vt/offline-fixture.json。执行器、制造错误代码 faults.mjs、判定代码 judge.mjs 分离；差异测试的预期独立写死，不使用执行器比较函数生成预期。

## 权限与已知边界

GitHub连接限目标仓库：Contents读写；改工作流另需Workflows写；运行需Actions读写。Notion连接必须有样本、测试文档、存档和新总表的访问权限，仓库 Secret 为 NOTION_TOKEN。令牌不要写入代码或日志。

复制仍使用Notion Markdown接口，不是递归Duplicate。核验沿用既有标准化哈希，会忽略评论元信息、行尾空白和某些链接显示形式，不能证明任意原始块结构或任意链接显示文字绝对一致。文档带子页时开始前停止。尚无跨进程锁、完整回滚、跨请求幂等、创建结果不明的持久恢复；不要在状态不明时盲目重跑。差异比较聚焦二级标题；不确定对应时报告待核对。v5发布是否通过，以实际运行证据为准，不以本README宣称通过。
