# doc-version-executor

版本管理执行器修正版 V5 候选代码，以及 VT01–VT39 测试工具。尚未进行本候选版本的真实 Notion 验收；旧 dev5 的运行结果不能算作本版本的结果。

## 测试前必须明确什么

每项先写定「测试什么」「测试错误」「正确结果」「首次引入版本」和固定原始样本。正常测试的「测试错误」注明正常输入、无故障注入；有故障的注明发生时机及次数。独立判定程序检查真实输出，不接受执行器自报成功作为通过依据。

- `executor.mjs`：被测执行器；不读取测试编号、测试总表、预期或故障代码。本次不改变其文件内容。
- `vt/cases.mjs`、`vt/faults.mjs`、`vt/judge.mjs`：原有 VT01–VT23 的配置、故障和独立判定。
- `vt/scenarios.mjs`、`vt/all-cases.mjs`：VT24–VT39 的普通编辑请求、预先写定的影响位置和 39 项统一清单。
- `vt/extra-faults.mjs`：在 VT39 的三次版本写入中保留旧顶部时间，核验执行器是否发现并正确失败。
- `vt/scenario-judge.mjs`：沿用原独立判定，并检查新测试的实际影响位置、顶部时间、故障次数。
- `vt/samples.json`、`vt/samples-new.json`：固定原始输入和上一版副本的真实页面编号；新样本附内容指纹，变化时停止而非悄悄换输入。
- `vt/preflight.mjs`：写入前读取 Notion 规则全文、核对仓库规则、表结构、预先设计、原始样本链接与运行编号。只约束此运行入口，不是 Notion 全局权限锁。
- `vt/run-vt.mjs`：先复制到独立工作页，再进行普通修改、运行执行器、读回独立判定、登记结果。原始样本和旧运行记录不被覆盖。
- `TESTING_RULES.md`：与 Notion 前置规则正文同步。改规则时两处都必须同步。

## 怎么在 Actions 跑测试

1. 打开 Actions → **VT 版本协议测试** → **Run workflow**。
2. 在 **Use workflow from** 中选择要验收的分支 `v5-tests-vt24-39`，或人工合并后选择 `main`。不能只看分支名，要核对运行页面记录的提交。
3. 测试编号填 `VT01` 等单项，或 `all`（VT01–VT39 全部）。
4. 确认后点击 Run workflow。这会读写真实 Notion，新建工作页、副本并写测试总表。
5. `plan` 先做结构及离线检查，然后每个 VT 是独立任务；单项失败不取消后面的项目，最多同时跑一个。
6. 查看每项日志中的预设事故、检查明细及「判定」。日志另存为 artifacts；Notion 表内记录实际执行器版本、运行时间、工作页及 GitHub 运行链接。

仓库需已有 `NOTION_TOKEN` secret，且该 Notion 连接对测试入口、原始样本、测试文档及副本存档具有所需权限。不要把密钥写进代码、URL 或聊天。

VT24–VT39 已有未跑行，首次真实运行填这些行。已有运行结果的测试追加下一次编号，保留旧结果。首次引入版本表示测试类别何时出现；执行器版本只在实际运行后写入，二者不能混用。

## 代码修改流程

AI 只把修改推送到分支，不开启、不修改、不合并 PR，也不启动 Actions。由人审阅差异、决定是否合并、何时运行测试。详见 `TESTING_RULES.md` 第七节。

## 离线检查与真实性

```sh
node verify-release.mjs
node vt/change-tests.mjs
```

离线快照核验可使用 `node vt/run-vt.mjs --case VT24 --offline /path/to/cache.json`，只写内存，不写真实 Notion，也不登记真实通过。快照文件为页面编号到 Markdown 的 JSON 映射，应通过有权限的读取取得，不在仓库发布工作区快照。

`vt/mutate.mjs` 的已有故障预测范围仍为 VT01–VT23，不能将其解释为新测试已经完成全部改坏覆盖。页面内容核验沿用 Markdown 标准化规则，不等于任意原始块结构完全一致的证明。

正式版本管理仍通过另一个工作流「正式运行：版本管理」触发，不要把它当作 VT 测试入口。对话授权按钮及全局受控写入权限仍需单独部署验证；本分支的前置检查不冒充全局技术门。
