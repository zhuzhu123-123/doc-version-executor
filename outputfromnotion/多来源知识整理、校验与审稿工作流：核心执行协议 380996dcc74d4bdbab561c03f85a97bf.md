## 一、目标｜形成完整、稳定、可核验的正式文档

本协议用于把主题材料、已有正文、人类评论、新材料和可核验来源整理成结构完整、可以独立阅读、可以核验和长期保存的正式文档。

调用本协议并完成一次正式确认后，AI必须执行到验收和版本管理结束，不得自行降级为普通润色、摘要或局部回答。

全程要求：

- 基于材料、证据、逻辑、前提、适用范围和风险判断，不奉承、不迎合、不把推测写成事实；
- 只修改落实本次确认要求所必需的位置，其他内容默认保持不变；
- 页面、评论、材料、来源或工具无法完整读取时，如实说明已读取和未读取范围；
- 删除重复和过程性解释，保留结果、必要理由、来源和限制。

## 二、适用范围｜创建新文档与修订已有文档

本协议处理两类任务：

1. **创建新文档**：根据主题、问题、材料和输出要求形成第一版正式正文；
2. **修订已有文档**：根据当前正式正文、人类修改、评论、新材料和新要求形成下一版正式正文。

普通临时问答、尚未形成正式结果的讨论和未完成草稿，不触发正式版本管理。

创建任务不虚构旧版本、旧差异或旧评论。修订任务必须以当前可靠正式版本为基准。

## 三、输入｜读取完成任务所需的材料

### 创建任务

执行前读取：

- 主题和具体问题；
- 人类提供的材料；
- 目标读者；
- 输出要求；
- 人类确认的任务范围。

### 修订任务

执行前读取：

- 当前可靠正式版本；
- 基准后的正文修改和评论；
- 可读取的建议修改；
- 新材料、新来源和对话要求；
- 人类确认的修改要求。

人类只需要确认修改要求，不逐项列出其他章节不得修改。AI根据已确认要求计算全部实际影响位置；落实该要求所必需的位置属于本次修改范围，其他无关内容默认受到保护。

输入不足以完成任务时，停止受影响部分并说明缺失内容，不凭记忆或猜测继续。

## 四、角色与责任｜人类确认要求，AI执行流程

| 角色 | 责任 |
| --- | --- |
| 人类 | 提出目标和修改要求，决定取舍，并对AI整理出的本次执行范围进行一次正式确认。 |
| AI | 读取材料，提取稳定要求，建立全文影响映射，整理多来源材料，编排结构，写作、标注、验收并调用必要专项协议。 |
| 来源协议 | 负责外部来源的主动检索、已有来源核验、来源基本信息，以及来源中与正文直接相关的主要内容。 |
| 版本管理协议 | 负责版本编号、版本记录、完整副本写入、独立复读与哈希核验，以及副本链接回填。 |

AI在正式写入前必须把准备执行的对象、要求和影响范围整理清楚；人类确认“按此执行”构成本轮唯一一次正式确认。确认后不在版本管理前重复要求人类确认。

## 五、执行步骤｜确定内容、影响范围和全文结构

本章完成分析和结构设计，不提前写正式正文，也不提前引用第六章尚未读取的输出规则。

### 创建新文档

```
读取主题、材料和输出要求
→ 区分事实、观点、案例、推测和AI生成内容
→ 需要外部依据时调用来源协议
→ 比较材料的一致、互补、冲突和适用范围
→ 确定内容归属和正文结构
→ 形成可以开始写作的完整结构
```

### 修订已有文档

```
确定当前可靠正式版本
→ 读取该版本之后的人类修改意见、评论、标注和新增材料
→ 把问题描述、批评和修改要求转换成不依赖聊天历史的稳定要求
→ 检查标题、正文、表格、示例、流程、验收、返工分支和完成条件等全部可能受影响的载体
→ 只确定为了落实稳定要求必须一起修改的位置
→ 原内容没有有效信息时直接删除
→ 原内容同时包含有效与错误信息时，提取有效信息并在正确位置统一重写
→ 确定需要替换、合并、移动或补充的其他内容
→ 形成可以开始写作的完整修改方案
```

### 来源核验最小接口

- **触发条件：**正文涉及需要外部依据的事实、数据、论文、书籍、理论、人物观点、机构、政策、产品、新闻、医学、法律、投资、安全或行业判断；
- **调用协议：**[来源检索、核验与说明：通用执行协议](https://app.notion.com/p/d9f4c1bdc53b40028a89f5d9e642040f?pvs=21)；
- **最低结果：**取得来源是否可用、与正文直接相关的主要内容和完整来源说明；
- **失败阻断：**没有取得可靠来源或原文不能支持主张时，不得写成确定结论。

## 六、输出｜按照完整规则生成正式正文

进入本章后，AI必须先读取本章全部输出规则和完整黑名单，再按照第五章确定的结构生成正式正文。

### 1. 正文输出规则

- 正文直接呈现当前有效的知识、规则、方法和步骤；
- 标题直接命名稳定对象，不把人类问题、修改动作或讨论过程写成标题；
- 不把聊天轮次、版本过程、错误修复过程和即时性表达写入普通正文；
- 不按人类修改意见出现的顺序追加补丁，不同时保留新旧两套表达；
- 错误内容没有有效信息时直接删除；同时包含有效与错误信息时，只提取有效信息并在正确位置统一重写；
- 正文不得加入“删除了什么、取消了什么、上一版为什么错误”等修改过程说明；
- 每句话或每段内容只表达当前有效的定义、规则、条件、边界和结果；如果一段内容只有结合旧版本、以前的讨论或修改过程才能理解，就不能放进普通正文；
- 一项修改需要同时调整多个位置时，按照第五章确定的位置一起修改；
- 正文必须能够脱离当前对话独立阅读和理解。

    - **补丁式追加**：再补充一点、这里增加一个说明、另外说明一下、再加一段、在原来的基础上补充、针对上一版补充、还需要补一句、下面再增加、最后再补充；
    - **修订历史依赖表达**：新增的理解、刚补充的内容、这次修正、本次修改、刚才的回答、前面的讨论、后面的内容、下面会讲、上面已经说过、如前所述、见上文、见下文、之前写错了、这里重新解释、原来的说法不准确、这一版改成、刚才漏掉了、虽然已经取消、原方案是、旧分类包括、修改后不再采用、与原来不同的是、为了避免再次出现、过去采用的是、原先还包括、这里仍需说明。

AI发现正文中出现黑名单词语后，必须检查整句话实际表达了什么，不能只删除那个词。即使一句话没有使用黑名单中的词，只要它离开当前对话、旧版本或修改过程就无法理解，也要按照同类问题修改。

检查方法：

1. 如果读者没有看过旧版本、评论和修改过程，这句话能否独立理解；
2. 这句话对理解或执行当前正文是否有实际作用；
3. 只用于说明旧版本、以前的讨论或修改过程的内容应当删除；
4. 一句话既有当前需要的信息，又混有修改过程时，只保留有用信息并重新写清楚；
5. 如果否定内容本身规定了当前规则、边界、风险或概念关系，应当保留。

处理方式：

| 问题类型 | 处理动作 |
| --- | --- |
| 相对时间 | 时间有长期价值时改成明确日期；没有价值时删除。 |
| 位置或对象指代 | 写明具体章节、规则、对象或概念名称。 |
| 问题式标题 | 改成知识、规则、对象、方法或步骤标题。 |
| 补丁式追加 | 返回正确语义位置，执行替换、合并、移动或结构重写。 |
| 只在了解旧版本或修改过程后才有意义的内容 | 只包含旧版本或修改过程时删除；同时包含当前需要的信息时，只保留有用信息并重新写清楚。 |

### 3. 黄红标注

黄色记录真正影响事实、判断、行动、结构或风险的原文问题；红色记录对应校正。每一处实质修改就地使用：

> **【原文问题｜对应版本｜问题类型｜原位置｜记录时间】** 问题说明。
> 

> **【校正意见｜执行主体｜操作时间｜修改动作｜实际影响位置】** 校正说明。
> 

对应版本、执行主体、时间、问题类型和位置不得省略，时间精确到分钟。黄色和红色标注按照固定格式，就地记录原文问题和对应校正。同一章节的黄红标注统一置于该章全部正式正文之后、下一章标题之前；同一章节存在多组标注时，按照对应修改在正文中的先后顺序排列。

### 4. 来源证据

正文保留与主张对应的引用编号，以及会改变读者理解、结论强度或行动判断的必要限制。完整来源资料按照[来源检索、核验与说明：通用执行协议](https://app.notion.com/p/d9f4c1bdc53b40028a89f5d9e642040f?pvs=21)，使用折叠区块紧跟其支持的段落、表格或章节。

### 5. 完整格式

完成后的页面包括：

- 完整正式正文；
- 就地黄红标注；
- 必要来源、引用。

## 七、验收｜按照Workflow顺序检查

验收按照执行过程从上到下进行。每组保留完成该Workflow所需的全部条件，不限制条件数量，也不把不同阶段的要求平铺混合。

### 1. 输入、范围与人类确认

- 创建或修订路径的必做步骤已经执行；
- 人类的问题描述、批评和修改要求已经转换成不依赖聊天历史的稳定要求；
- 人类确认的要求均已落实；
- 输入材料、页面、评论和确认范围已经完整读取；未完成或无法核验的内容已经明确说明。

### 2. 正文生成、删除、统一重写与影响位置

- 标题、正文、表格、示例、流程、验收、返工分支和完成条件中，为了落实稳定要求而必须一起修改的位置都已经处理；
- 未涉及本次要求的内容保持不变；
- 正文结构完整，没有重复、矛盾、新旧内容同时存在或相关步骤遗漏；
- 黑名单中的表达和意思相同的其他说法都已经处理；
- 旧句删除后，旧要求没有换一种措辞、分类或结构继续残留；
- 没有看过旧版本、评论和修改过程的读者也能独立理解正文；
- 只用于说明旧版本或修改过程的内容已经删除；同时包含当前信息和修改过程的内容已经重新写清楚；

### 3. 评论、黄红标注与来源

- 纳入修改范围的人类评论已经落实；未落实的评论已经说明原因、失败位置和下一步；
- 每个实质修改章节都有对应的黄红标注；标注格式正确，并放在该章正文末尾、下一章标题之前；
- 引用与正文主张对应；来源基本信息、来源主要内容及其与正文直接相关的内容已经写清楚；正文没有歪曲或扩大来源内容。

### 4. 运行故障、版本管理与结束

- 运行故障已经恢复并重新验收；仍未恢复时，本轮修改失败；
- 前三组条件全部通过后，必须调用版本管理协议；
- 版本记录、完整副本、副本哈希核验和链接回填全部完成，并取得“版本成立”，核心Workflow才能结束。

## 八、验收返工与真正运行异常

### 1. 验收未通过后的阻断、修正与产品改进

第五至七章通过稳定要求、影响位置检查、删除与统一重写、范围保护和验收措施预防已知错误。本节不把这些错误视为可以长期接受的结果，而是在预防措施仍未生效时阻止不合格正文进入版本管理，并把结果返回对应步骤修正。

```
正常流程措施预防错误
→ 第七章验收措施是否生效
→ 验收通过：进入版本管理
→ 验收未通过：阻断输出并返回对应步骤修正
→ 同类问题反复发生：记录为产品缺陷，更新正常流程措施并增加回归测试
```

| 验收发现的问题 | 立即阻断与修正 | 反复发生后的产品改进 |
| --- | --- | --- |
| 应该一起修改的位置没有全部处理 | 回到第五章，重新检查全部影响载体和文章结构；补全后重新验收。 | 改进影响位置识别规则，并增加标题、正文、表格、示例、流程和验收同时受影响的测试案例。 |
| 修改后出现重复、矛盾或内容放错位置 | 回到第五章，重新确定内容归属并统一调整相关位置。 | 检查内容归属和结构设计为什么失效，补充结构冲突与重复内容的回归测试。 |
| 正文仍带有对话、即时提问、修改过程或补丁式表达 | 回到第六章；没有有效信息的内容直接删除，混合内容提取有效信息并统一重写。 | 扩充历史语言和补丁式表达检查，并增加纯删除、混合重写和多轮反馈测试。 |
| 旧句已经删除但旧要求仍以同义表达、分类或结构残留 | 回到第五章重新识别语义影响位置，并在第六章生成唯一的当前规则。 | 补充同义表达、分类替换和结构残留测试，改进语义残留检查。 |
| 评论、来源或其他确认要求尚未落实 | 返回对应正常步骤处理；全部完成后重新执行第七章验收。 | 检查要求提取、状态记录和完成验收是否存在缺口，补充遗漏要求测试。 |
| 来源无效、不能支持正文或仍需追溯 | 按照来源协议的正常结果分支继续处理，不写入确定结论。 | 根据失败分布改进检索方向、证据提取、停止条件或来源验收测试。 |

单次验收失败由对应步骤修正；同类失败达到需要关注的频率或风险等级时，不得继续把返工作为固定解决方式。产品迭代必须分析现有措施为什么没有生效，修改第五至七章的预防或验收规则，并把失败案例加入固定测试集。

### 2. 真正运行异常

真正异常只包括流程无法提前消除的运行故障：

| 运行异常 | 处理方法 |
| --- | --- |
| 页面、评论或必要材料无法读取 | 记录已读取和未读取范围，停止受影响步骤；恢复访问后从中断位置继续。 |
| 搜索、读取、解析、数据库或写入工具超时、限流或失败 | 记录失败工具、步骤和影响范围；按风险重试或使用允许的备用入口，仍失败时安全停止。 |
| 权限不足、登录失效或访问受限 | 确认可访问范围；无法取得必要内容时不得声称完成。 |
| 状态保存、版本记录或副本建立失败 | 保留可恢复信息，阻止任务结束；修复后重新验收或重新调用版本管理。 |

正常返工或异常恢复后，必须重新执行第七章验收。仍不能通过时，说明具体问题、失败位置和已完成范围，本次修改失败，不进入版本管理。

## 九、版本管理｜通过验收后建立正式版本

### 版本管理最小接口

- **触发条件：**核心Workflow完成本次确认范围并通过自身全部验收；
- **调用协议：**[AI 与人类协作文档版本管理：执行协议](https://app.notion.com/p/AI-3fb8ad5870e34d94aaeeff0cb3a3e600?pvs=21)；
- **最低结果：**版本管理协议确认“版本成立”；
- **失败阻断：**版本管理返回失败时，本轮核心Workflow不得宣布完成。

当前最新正式版本是本协议的执行依据；历史版本和版本记录用于追溯。

正式文档内容包括当前有效正文、必要黄红标注和来源；完整Workflow交付结果还包括版本记录、完整副本、副本哈希核验和副本链接回填。版本管理协议没有确认“版本成立”时，不得宣布本轮工作完成。

版本成立后，本轮Workflow结束。以后出现新要求时，重新启动新一轮输入、范围确认和执行。
